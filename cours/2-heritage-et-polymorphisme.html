Héritage et polymorphisme

Le problème : du code en double

class Student {

    string name;

    string group;

class Teacher {

  • name, email et introduce() sont écrits deux fois : chaque correction devra être faite deux fois
  • Un étudiant est une personne, un professeur est une personne : ce qu'ils ont en commun peut aller dans une classe Person

Hériter d'une classe

  • Une classe fille (ou dérivée) hérite de tous les attributs et de toutes les méthodes de sa classe mère (ou de base)
  • Elle y ajoute ce qui lui est propre
  • Syntaxe : class Student : public Person { … };
  • La règle pour savoir si l'héritage a du sens : on doit pouvoir dire « une Student est une Person ». Un étudiant n'est pas un ordinateur : là, c'est de la composition

protected et redéfinition

Héritage et polymorphisme

Le droit d'accès protected

Une méthode de Student ne peut pas lire name s'il est private dans Person : private réserve l'accès à la classe elle-même, pas à ses filles.

Droit d'accèsLa classeSes classes fillesLe reste du programme

Dans une classe mère, on déclare en protected les attributs dont les filles ont besoin. L'encapsulation est respectée : main n'y a toujours pas accès.

  • Apprentice peut appeler study(), héritée de Student, et work(), héritée d'Employee
  • Les constructeurs mères sont appelés dans l'ordre où les classes sont déclarées après les deux-points

Les pièges de l'héritage multiple

Deux méthodes de même nom

Si Student et Employee ont toutes les deux une méthode display(), l'appel cosmo.display() est ambigu : erreur de compilation.

Solutions : préciser la classe, cosmo.Student::display();, ou redéfinir display() dans Apprentice.

Le problème du losange

Si Student et Employee héritent toutes les deux de Person, un Apprentice contient deux parties Person, donc deux noms.

C++ le résout avec l'héritage virtuel, hors programme.

Conseil : réservez l'héritage multiple aux cas où la seconde classe mère apporte une capacité indépendante (savoir lancer des sorts, savoir s'afficher…), sans ancêtre commun avec la première.

Héritage et polymorphisme

Le problème : un professeur qui s'ignore


#include <iostream>
#include <string>
using namespace std;

class Person {
protected:
    string name;
public:
    Person(string newName) : name(newName) {}
    void introduce() const {
        cout << "Je suis " << name << endl;
    }
};

class Teacher : public Person {
public:
    Teacher(string newName) : Person(newName) {}
    void introduce() const {
        cout << "Professeur " << name << endl;
    }
};
        

void welcome(const Person& person) {
    person.introduce();
}

int main() {
    Person manon("Manon");
    Teacher chris("Chris");
    chris.introduce();
    welcome(manon);
    welcome(chris);
    return 0;
}
          
Professeur Chris
Je suis Manon
Je suis Chris
  • Pour une Person&, le compilateur choisit Person::introduce(), même pour Chris
Un professeur est une personne, donc welcome accepte un Teacher. Mais le choix de la méthode se fait sur le type déclaré du paramètre.

La solution : une méthode virtuelle


#include <iostream>
#include <string>
using namespace std;

class Person {
protected:
    string name;
public:
    Person(string newName) : name(newName) {}
    virtual void introduce() const {
        cout << "Je suis " << name << endl;
    }
};

class Teacher : public Person {
public:
    Teacher(string newName) : Person(newName) {}
    void introduce() const override {
        cout << "Professeur " << name << endl;
    }
};
        

void welcome(const Person& person) {
    person.introduce();
}

int main() {
    Person manon("Manon");
    Teacher chris("Chris");
    welcome(manon);
    welcome(chris);
    return 0;
}
          
Je suis Manon
Professeur Chris
  • virtual : la méthode est choisie selon le vrai type de l'objet, à l'exécution
  • override : le compilateur vérifie qu'une méthode virtuelle est bien redéfinie

Le polymorphisme en résumé

  • Polymorphisme : « plusieurs formes ». Le même appel, person.introduce(), se comporte différemment selon le type réel de l'objet
  • Résolution statique : sans virtual, le compilateur choisit la méthode d'après le type déclaré de la variable
  • Résolution dynamique : avec virtual, le programme choisit la méthode d'après le type réel de l'objet, pendant l'exécution
Les deux ingrédients du polymorphisme

1. Une méthode virtual dans la classe mère.

2. Un accès par référence (Person&) ou par pointeur (Person*). Avec une simple copie, l'objet perd sa partie fille.

Qu'affiche ce programme ?


#include <iostream>
using namespace std;

class Message {
public:
    virtual void send() const {
        cout << "Message" << endl;
    }
};

class Email : public Message {
public:
    void send() const override {
        cout << "E-mail" << endl;
    }
};
        

void sendCopy(Message message) {
    message.send();
}

void sendRef(const Message& message) {
    message.send();
}

int main() {
    Email email;
    email.send();
    sendCopy(email);
    sendRef(email);
    return 0;
}

Message : la copie ne garde que la partie Message de l'objet

Les collections d'objets

Héritage et polymorphisme

Le tableau dynamique vector


#include <iostream>
#include <vector>
using namespace std;

int main() {
    vector<int> grades = {12, 15, 9};
    grades.push_back(17);
    cout << grades.size() << " notes" << endl;
    cout << "Première : " << grades[0] << endl;

    int total = 0;
    for (int grade : grades) {
        total = total + grade;
    }
    cout << "Total : " << total << endl;
    return 0;
}
  • vector<int> est une liste d'entiers, comme une liste Python. Entre chevrons, le type des éléments
  • push_back() ajoute à la fin, comme append()
  • size() donne le nombre d'éléments, [0] le premier
  • for (int grade : grades) parcourt la liste, comme for grade in grades

Les pointeurs

  • Un vector<Person> range des copies : un professeur y perdrait sa partie Teacher
  • On range donc des pointeurs : vector<Person*>
  • Un pointeur contient l'adresse d'un objet en mémoire. Il ne copie pas l'objet, il indique où le trouver
  • &chris donne l'adresse de chris. -> appelle une méthode à travers un pointeur
  • nullptr est un pointeur qui ne pointe sur rien
Teacher chris("Chris");
Person* pointer = &chris;

pointer->introduce();
// Professeur Chris
// si introduce() est virtuelle
Une référence est un autre nom pour un objet ; un pointeur est une variable qui contient une adresse et peut changer de cible. On ne peut pas ranger des références dans un vector, d'où les pointeurs.

new, delete et destructeur virtuel


#include <iostream>
using namespace std;

class Message {
public:
    virtual ~Message() {
        cout << "- Message" << endl;
    }
};

class Email : public Message {
public:
    ~Email() override {
        cout << "- Email" << endl;
    }
};
          

int main() {
    Message* message = new Email();
    delete message;
    return 0;
}
          
- Email
- Message
  • new crée un objet qui survit à la fin du bloc et renvoie son adresse
  • Autant de delete que de new, sinon la mémoire n'est jamais libérée : c'est une fuite de mémoire
  • Sans virtual devant ~Message(), la partie Email ne serait pas détruite : une classe mère polymorphe a toujours un destructeur virtuel
  • En C++ moderne, std::unique_ptr détruit l'objet tout seul

Les classes abstraites

Héritage et polymorphisme

La méthode virtuelle pure

  • Une évaluation a une note. Mais comment calculer la note d'une évaluation « en général » ? Elle dépend du type : partiel, quiz, projet…
  • On déclare la méthode sans l'écrire, avec = 0 : c'est une méthode virtuelle pure. Chaque classe fille doit l'écrire
  • Une classe qui a au moins une méthode virtuelle pure est une classe abstraite : on ne peut pas créer d'objet de ce type
virtual double score() const = 0;
Evaluation oral("Oral");
error: cannot declare variable 'oral'
to be of abstract type 'Evaluation'

Une classe abstraite en pratique


#include <iostream>
#include <string>
#include <vector>
using namespace std;

class Evaluation {
protected:
    string label;

public:
    Evaluation(string newLabel)
        : label(newLabel) {
    }
    virtual ~Evaluation() {
    }
    virtual double score() const = 0;
    void display() const {
        cout << label << " : " << score()
             << "/20" << endl;
    }
};
        

class Exam : public Evaluation {
private:
    double grade;

public:
    Exam(string newLabel, double value)
        : Evaluation(newLabel), grade(value) {
    }
    double score() const override {
        return grade;
    }
};
  • display() n'est pas virtuelle, mais elle appelle score(), qui l'est : chaque évaluation affiche sa propre note
  • Exam écrit score() : elle n'est plus abstraite, on peut créer des examens

Une classe abstraite en pratique (suite)


class Quiz : public Evaluation {
private:
    int correct;
    int total;

public:
    Quiz(string newLabel, int good, int count)
        : Evaluation(newLabel), correct(good),
          total(count) {
    }
    double score() const override {
        return 20.0 * correct / total;
    }
};

int main() {
    Exam partial("Partiel", 14);
    Quiz kahoot("Kahoot", 8, 10);
    vector<Evaluation*> evaluations;
    evaluations.push_back(&partial);
    evaluations.push_back(&kahoot);
        
    double sum = 0;
    for (Evaluation* evaluation : evaluations) {
        evaluation->display();
        sum = sum + evaluation->score();
    }
    cout << "Moyenne : "
         << sum / evaluations.size() << endl;
    return 0;
}
Partiel : 14/20
Kahoot : 16/20
Moyenne : 15
  • La boucle ne sait pas quel type d'évaluation elle traite : c'est le polymorphisme qui choisit le bon score()
